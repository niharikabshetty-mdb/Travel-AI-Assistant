# 2.2 Node.js & Middleware Architecture

## 1. Overview

The Travel AI Assistant uses Node.js as a gateway layer between the Next.js frontend and the FastAPI backend.

The Node.js gateway is built using Express.js.

Its main responsibilities are:

- Receiving requests from the Next.js frontend
- Creating request IDs for tracking
- Authenticating users using Firebase ID tokens
- Forwarding valid travel planning requests to FastAPI
- Saving generated itineraries to MongoDB Atlas
- Returning responses to the frontend
- Handling backend errors

The architecture is:

```text
Next.js Frontend
       ↓
Node.js / Express Gateway
       ↓
FastAPI Backend
       ↓
OpenAI

MongoDB is also accessed by the Node.js gateway for storing generated trips.

2. Why Node.js is Used

Node.js is used as an intermediate gateway instead of allowing the frontend to communicate directly with the FastAPI AI backend.

This provides a central layer for:

Authentication
Request processing
Logging
Error handling
Database operations
Communication between frontend and backend services

This approach also makes the system easier to extend in the future.

6. Middleware

Middleware is one of the important concepts in the Node.js gateway.

Middleware is a function that runs during the processing of an HTTP request.

A simplified request flow is:

Client Request
      ↓
Middleware
      ↓
Route Handler
      ↓
Response

Middleware can:

Inspect requests
Modify requests
Add information to requests
Authenticate users
Log requests
Reject invalid requests
Pass control to the next middleware or route
7. Request Logging Middleware

The Travel AI Assistant contains request logging middleware.

The middleware generates a unique request ID:

app.use((req, res, next) => {
  const requestId = `REQ-${Date.now()}`;

  req.requestId = requestId;

  console.log(
    `[${new Date().toISOString()}] ${req.method} ${req.originalUrl} | ${requestId}`
  );

  next();
});
What it does

Whenever a request reaches the Node.js server:

A request ID is generated.
The request ID is attached to the request.
The HTTP method is logged.
The requested URL is logged.
next() passes control to the next middleware or route.

For example:

GET /health

may produce a log similar to:

[2026-09-15T...] GET /health | REQ-...

This is useful for debugging and tracking requests.

8. What is next()?

The next() function tells Express that the current middleware has finished its work.

For example:

app.use((req, res, next) => {
  console.log("Request received");

  next();
});

Without next() or a response being sent, the request could remain stuck.

The request flow is therefore:

Request
   ↓
Logging Middleware
   ↓
next()
   ↓
Authentication Middleware
   ↓
next()
   ↓
API Route
   ↓
Response
9. Firebase Authentication Middleware

The application contains authentication middleware called:

authenticateUser

Its purpose is to verify that the request comes from an authenticated Firebase user.

The frontend sends the Firebase ID token using:

Authorization: Bearer <Firebase ID Token>

The middleware first checks whether the authorization header exists.

If it does not exist, the request is rejected:

{
  "success": false,
  "error": "Authentication required"
}
10. Authorization Header Validation

The middleware checks that the authorization header starts with:

Bearer

The expected format is:

Authorization: Bearer TOKEN

If the format is incorrect, the server returns:

{
  "success": false,
  "error": "Invalid authentication format"
}

This prevents incorrectly formatted authentication requests from continuing.

11. Firebase ID Token Verification

After extracting the token, the Node.js gateway verifies it using the Firebase Admin SDK.

Conceptually:

const decodedToken =
  await adminAuth.verifyIdToken(idToken);

If the token is valid, Firebase returns information about the authenticated user.

The decoded information is stored in:

req.user = decodedToken;

This makes the authenticated user's information available to later route handlers.

For example:

req.user.uid

contains the user's Firebase UID.

The email can be accessed through:

req.user.email

when available.

12. Authentication Request Flow

The complete authentication flow is:

User
 ↓
Logs in through Firebase
 ↓
Firebase creates authentication session
 ↓
Frontend obtains Firebase ID token
 ↓
Frontend sends token to Node.js
 ↓
Node.js authentication middleware
 ↓
Firebase Admin verifies token
 ↓
User authenticated
 ↓
Request continues

If authentication fails:

Invalid Token
     ↓
Node.js rejects request
     ↓
HTTP 401
13. Protected API Routes

The authentication middleware is applied to protected routes.

For example:

app.post(
  "/api/plan",
  authenticateUser,
  async (req, res) => {
    // travel planning logic
  }
);

The order is important:

POST /api/plan
      ↓
authenticateUser
      ↓
Travel Planning Route

Therefore, the travel planning route only executes after successful authentication.

14. Health Endpoint

The gateway provides a health endpoint:

GET /health

It can be accessed using:

http://localhost:5000/health

The endpoint reports whether the Node.js gateway is running and whether MongoDB is connected.

An example response is:

{
  "success": true,
  "message": "Node.js gateway is running",
  "mongodb": "connected"
}

This endpoint does not require Firebase authentication because it is intended for service health checking.

15. MongoDB Test Endpoint

The gateway also contains:

It verifies that the server can communicate with MongoDB Atlas.

The endpoint can also return the collections available in the configured database.

16. Authentication Test Endpoint

The gateway contains another protected endpoint:

If authentication succeeds, it returns information about the authenticated user.

This endpoint is useful for testing the authentication integration independently from travel planning.

18. Forwarding Requests to FastAPI

After authentication succeeds, the Node.js gateway sends the travel request to FastAPI.

The FastAPI service runs locally at:

http://127.0.0.1:8000

The Node.js gateway forwards the request to:

http://127.0.0.1:8000/api/plan

Axios is used for this communication.

Conceptually:

const response = await axios.post(
  `${FASTAPI_URL}/api/plan`,
  req.body
);

The request body received from the frontend is forwarded to FastAPI.

22. Error Handling

The Node.js gateway handles errors that may occur during:

Authentication
FastAPI communication
AI itinerary generation
MongoDB operations

For example, if FastAPI returns an error, the Node.js gateway can return an appropriate error response to the frontend.

A generic server-side error response is:

{
  "success": false,
  "error": "Unable to generate or save the travel itinerary."
}

Error messages are also logged in the Node.js terminal to assist with debugging.

23. CORS

The gateway uses the CORS package:

const cors = require("cors");

and enables it using:

app.use(cors());

CORS allows the frontend and backend services running on different local ports to communicate during development.

For example:

Next.js
localhost:3000
       ↓
Node.js
localhost:5000

Without appropriate CORS handling, browser security rules could prevent the frontend from making the request.

26. Why Middleware is Important

Middleware provides a clean way to implement functionality that should happen before a request reaches the main API logic.

In this project, middleware is used for:

Request Tracking

A request ID is created for each request.

Authentication

Firebase tokens are verified before protected routes execute.

Request Control

Invalid requests can be rejected before they reach the application logic.

This prevents authentication and request-processing logic from being duplicated inside every protected route.

serviceAccountKey.json
