# 2.4 Firebase & Firebase Authentication

## 1. Introduction

Firebase is a platform provided by Google that offers services for building and managing web and mobile applications.

In the Travel AI Assistant project, Firebase is mainly used for **user authentication**.

The application uses Firebase Authentication to allow users to:

- Create an account
- Log in securely
- Maintain an authenticated session
- Log out
- Access protected application features

Firebase is integrated with the Next.js frontend and the Node.js gateway.

The authentication flow is:

```text
User
 ↓
Next.js Login Page
 ↓
Firebase Authentication
 ↓
Authenticated Firebase User
 ↓
Firebase ID Token
 ↓
Node.js Gateway
 ↓
Firebase Admin SDK
 ↓
Protected API Access

2. Why Firebase Authentication Was Used

Authentication is important because the Travel AI Assistant should not allow unauthenticated users to access the main travel planning functionality.

Instead of implementing password storage and authentication logic manually, Firebase Authentication provides a secure and well-tested authentication service.

The main reasons for using Firebase Authentication are:

Easy integration with Next.js
Secure password authentication
Session management
Firebase client SDK
Firebase Admin SDK for backend verification
ID token based authentication
Reduced need to implement authentication infrastructure manually
3. Firebase Project Setup

A Firebase project was created for the Travel AI Assistant application.

The Firebase project is connected to the web application through the Firebase Web SDK.

The application uses the following Firebase configuration values:

apiKey
authDomain
projectId
storageBucket
messagingSenderId
appId

These values are loaded from environment variables in the Next.js frontend.

Example:

NEXT_PUBLIC_FIREBASE_API_KEY=...

The actual credentials are stored in the local .env.local file and are not committed to GitHub.

4. Firebase Authentication Method

The current application uses:

Email and Password Authentication

The user can either:

Create a new account
Sign in using an existing account

Other authentication methods such as Google Sign-In are not required for the current MVP.

5. Firebase Client SDK

The Firebase client SDK is used inside the Next.js frontend.

The Firebase initialization is implemented in:

frontend/lib/firebase.ts

The important imports are:

import { initializeApp, getApps, getApp } from "firebase/app";
import { getAuth } from "firebase/auth";

Firebase is initialized using:

const app =
  getApps().length === 0
    ? initializeApp(firebaseConfig)
    : getApp();

export const auth = getAuth(app);

This creates the Firebase application instance and the Firebase Authentication instance.

The exported auth object is used by the login page and protected pages.

6. Dedicated Login Page

Authentication is kept separate from the main travel assistant interface.

The login page is located at:

frontend/app/login/page.tsx

This page provides two modes:

Sign In
Create Account

The user does not need to select a Traveller/Admin role.

All authenticated users enter the same travel assistant application.

7. Creating a New Account

When a user creates an account, Firebase's:

createUserWithEmailAndPassword()

function is used.

The basic process is:

User enters email and password
        ↓
Next.js sends credentials to Firebase
        ↓
Firebase creates the account
        ↓
User becomes authenticated
        ↓
Application redirects to /home

The signup process does not require the application to store passwords itself.

Firebase handles the authentication credentials.

8. User Login

For an existing user, the application uses:

signInWithEmailAndPassword()

The process is:

User enters email and password
        ↓
Firebase verifies credentials
        ↓
Authentication succeeds
        ↓
User session becomes active
        ↓
User is redirected to /home

If the credentials are incorrect, an appropriate error message is displayed to the user.

9. Authentication State

After login, the application needs to know whether the user is authenticated.

The /home page uses:

onAuthStateChanged()

to monitor the Firebase authentication state.

The basic logic is:

Is the user authenticated?
        │
        ├── YES → Allow access to /home
        │
        └── NO  → Redirect to /login

This protects the main travel assistant interface from unauthenticated access.

10. Protected Home Page

The main application is available at:

/home

The page checks the Firebase authentication state before allowing the user to use the travel planning functionality.

If a user is not logged in, the application redirects them to:

/login

This creates a simple protected-route mechanism.

11. Firebase ID Token

Firebase provides an ID token for an authenticated user.

The frontend obtains the token using:

const idToken =
  await auth.currentUser?.getIdToken();

The ID token is then sent to the Node.js gateway.

The request contains:

Authorization: Bearer <Firebase-ID-Token>

This allows the backend to verify that the request comes from an authenticated Firebase user.

12. Sending the Token to Node.js

When the user requests an itinerary, the Next.js frontend sends the request to:

http://localhost:5000/api/plan

The request includes the Firebase ID token.

The structure is:

Next.js
   ↓
Firebase Authentication
   ↓
Get Firebase ID Token
   ↓
Authorization: Bearer <token>
   ↓
Node.js Gateway

The frontend therefore does not directly trust the user's login state when making backend requests.

The backend independently verifies the token.

13. Firebase Admin SDK

The Node.js gateway uses the Firebase Admin SDK.

The Admin SDK is used on the server side to verify Firebase ID tokens.

The Node.js gateway initializes Firebase Admin using the Firebase service account credentials.

The relevant packages are:

firebase-admin

The Admin SDK is different from the Firebase client SDK.

Firebase Client SDK

Used by:

Next.js frontend

Main purpose:

Sign up
Login
Logout
Authentication state
Get ID token
Firebase Admin SDK

Used by:

Node.js backend

Main purpose:

Verify ID tokens
Trust authenticated users
Protect backend routes
14. Firebase Authentication Middleware

The Node.js gateway contains an authentication middleware:

async function authenticateUser(req, res, next) {

This middleware checks the request's authorization header.

First it looks for:

Authorization

If the header is missing, the request is rejected.

Example:

if (!authorizationHeader) {
  return res.status(401).json({
    success: false,
    error: "Authentication required",
  });
}
15. Checking the Bearer Token

The application expects the authorization header to start with:

Bearer

The middleware checks:

if (!authorizationHeader.startsWith("Bearer ")) {

If the format is incorrect, the request is rejected.

The actual token is extracted using:

const idToken =
  authorizationHeader.substring(7);
16. Verifying the Firebase ID Token

The Firebase Admin SDK verifies the token using:

const decodedToken =
  await adminAuth.verifyIdToken(idToken);

If verification succeeds, Firebase provides information about the authenticated user.

The decoded token is stored in:

req.user = decodedToken;

The next middleware or route can then access the authenticated user's information.

17. Authentication Failure

If the token is:

Missing
Invalid
Expired
Incorrectly formatted

the backend rejects the request.

The application returns:

401 Unauthorized

For example:

{
  "success": false,
  "error": "Invalid or expired authentication token"
}

This prevents unauthenticated users from accessing protected backend endpoints.

18. Protected Backend Routes

The Firebase authentication middleware is applied to protected Node.js routes.

Currently protected routes include:

POST /api/test-auth
GET  /api/test-db
POST /api/plan

For example:

app.post(
  "/api/plan",
  authenticateUser,
  async (req, res) => {
    ...
  }
);

The authenticateUser middleware runs before the travel planning logic.

Therefore:

Request
   ↓
Authentication Middleware
   ↓
Token Valid?
   │
   ├── NO → 401 Unauthorized
   │
   └── YES → Continue to /api/plan
19. Test Authentication Endpoint

The application includes:

POST /api/test-auth

This endpoint is protected by Firebase authentication.

Its purpose is to verify that:

The frontend can obtain a Firebase ID token.
The token can be sent to Node.js.
Node.js can verify the token.
The authenticated user's information can be retrieved.

A successful response confirms that Firebase authentication is correctly integrated with the backend.

20. User Information

After successful token verification, the Node.js gateway can access information such as:

uid
email

The user ID is especially useful because it can be associated with application data.

For example, when a travel plan is saved to MongoDB, the application stores:

userId
userEmail

along with the itinerary.

This allows saved travel plans to be associated with the authenticated Firebase user.

21. Logout

The application also provides a logout option.

Firebase's:

signOut()

The process is:

User clicks Logout

        ↓

        ↓
User is redirected to /login

This prevents the user from continuing to access the protected home page after logging out.

23. Authentication Security

Several security practices are followed.

23.1 Passwords Are Not Stored Manually

The application does not implement its own password database.

Firebase Authentication manages email/password credentials.

23.2 Backend Token Verification

The Node.js gateway does not simply trust that the frontend says a user is logged in.

It verifies the Firebase ID token using the Firebase Admin SDK.

This provides backend-side authentication.

23.3 Service Account Protection

The Firebase Admin service account file is sensitive.

The project contains:

node-gateway/serviceAccountKey.json

This file must never be uploaded to GitHub.

It is included in .gitignore.

23.4 Environment Variables

Sensitive configuration values are stored using environment variables.

For example:

.env
.env.local

These files are ignored by Git.

The actual secret values should never be written directly into source code or documentation.

24. Firebase Client Configuration vs Server Credentials

It is important to distinguish between Firebase web configuration and Firebase Admin credentials.

The Firebase web configuration used by the frontend is designed to identify the Firebase project.

The Admin SDK service account contains sensitive server-side credentials.

Therefore:

Frontend Firebase Configuration
→ Used by browser

Firebase Admin Service Account
→ Used only by backend

The Admin credentials must remain private.

29. Role of Firebase in the Overall System

Firebase is responsible for authentication only.

The responsibilities are separated as follows:

Technology	Responsibility
Next.js	User interface
Firebase Authentication	User authentication
Node.js	Gateway and middleware
Firebase Admin SDK	Backend token verification
FastAPI	AI backend
OpenAI	Itinerary generation
MongoDB Atlas	Trip storage

This separation keeps the architecture easier to understand and maintain.

30. Conclusion

Firebase Authentication provides the authentication layer for the Travel AI Assistant.

Users can create accounts and log in using email and password through the dedicated Next.js login page.

After authentication, Firebase provides an ID token. The token is sent to the Node.js gateway using a Bearer Authorization header.

The Node.js gateway uses Firebase Admin SDK to verify the token before allowing access to protected endpoints.
