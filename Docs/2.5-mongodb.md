# 2.5 MongoDB & MongoDB Vector Search

## 1. Introduction

MongoDB is a NoSQL database that stores data in a flexible document-oriented format.

In the Travel AI Assistant project, MongoDB Atlas is used to store the travel itineraries generated for authenticated users.

The database is connected to the Node.js gateway.

The current data flow is:

```text
User
 ↓
Next.js Frontend
 ↓
Firebase Authentication
 ↓
Node.js Gateway
 ↓
FastAPI
 ↓
OpenAI
 ↓
Generated Itinerary
 ↓
Node.js Gateway
 ↓
MongoDB Atlas

MongoDB is therefore responsible for persistent storage of generated travel plans.

2. Why MongoDB Was Used

MongoDB was selected because travel itinerary data is naturally document-oriented.

A travel plan can contain:

Destination
Number of days
Number of travelers
Interests
Multiple itinerary days
Morning activities
Afternoon activities
Evening activities
Food recommendations
Daily tips
General travel tips
User information
Creation timestamp

This type of nested and flexible data can be represented naturally inside a MongoDB document.

The main advantages for this project are:

Document-based storage
Flexible schema
Support for nested objects and arrays
Easy integration with Node.js
Cloud-hosted MongoDB Atlas
Scalability
MongoDB Search and Vector Search capabilities for future extensions
3. MongoDB Atlas

The project uses MongoDB Atlas, which is the cloud-hosted version of MongoDB.

Instead of running the database completely on the local computer, the application connects to a MongoDB Atlas cluster.

The application uses a MongoDB database named:

IntelligentAssistant-cluster

The main collection used by the application is:

trips

The database structure is:

IntelligentAssistant-cluster
└── trips

5. MongoDB Environment Variables

The MongoDB connection details are stored in the Node.js environment file:

node-gateway/.env

The configuration contains:

MONGODB_URI=...
MONGODB_DB_NAME=IntelligentAssistant-cluster

The actual MongoDB connection string is kept secret and is not written into source code.

The .env file is included in .gitignore.

Therefore, database credentials are not pushed to GitHub.

6. MongoDB Connection

The Node.js gateway imports the MongoDB client:

const { MongoClient } = require("mongodb");

The connection string is loaded from the environment:

const MONGODB_URI = process.env.MONGODB_URI;

The database name is also loaded from the environment:

const MONGODB_DB_NAME =
  process.env.MONGODB_DB_NAME ||
  "travel_ai_assistant";

A MongoDB client is created:

const mongoClient =
  new MongoClient(MONGODB_URI);
7. Connecting to the Database

The Node.js gateway contains a connection function:

async function connectToMongoDB() {

The client connects using:

await mongoClient.connect();

After connecting, the application selects the database:

database =
  mongoClient.db(MONGODB_DB_NAME);

The trips collection is then selected:

tripsCollection =
  database.collection("trips");

The application also performs a ping operation:

await database.command({ ping: 1 });

This verifies that MongoDB is reachable.

8. MongoDB Connection Startup

MongoDB is connected before the Node.js server begins accepting requests.

The startup process is:

Start Node.js Gateway
        ↓
Connect to MongoDB Atlas
        ↓
Ping Database
        ↓
Connection Successful
        ↓
Start Express Server

If the MongoDB connection fails, the application reports the error and stops the server.

This prevents the application from running as if the database were available when it is not.

15. MongoDB Document Model

MongoDB stores data as documents.

Documents are similar to JSON objects.

For example:

{
  "destination": "Paris",
  "days": 4,
  "travelers": 2,
  "interests": [
    "art",
    "food"
  ]
}

Unlike a traditional relational database, MongoDB does not require every piece of data to be represented as rows in multiple tables.

Nested data can be stored directly inside a document.

This is useful for the itinerary structure because one trip can contain many days and each day can contain multiple pieces of information.

16. Arrays and Nested Documents

The itinerary contains nested data.

For example:

{
  "days": [
    {
      "day": 1,
      "title": "Arrival and City Exploration",
      "morning": "...",
      "afternoon": "...",
      "evening": "...",
      "food": [
        "...",
        "..."
      ],
      "tips": [
        "...",
        "..."
      ]
    }
  ]
}

MongoDB can store this nested structure directly.

This avoids unnecessarily splitting the itinerary into multiple database tables.

19. MongoDB Vector Search

MongoDB also provides Vector Search capabilities.

Vector Search is different from normal database searching.

Traditional search might look for:

"Paris"

and return documents containing the word Paris.

Vector Search works using numerical representations called embeddings.

An embedding represents the meaning of data as a vector of numbers.

For example:

Travel text
    ↓
Embedding Model
    ↓
Vector
    ↓
MongoDB Vector Search

Documents with similar meanings can then be retrieved based on vector similarity.

20. Why Vector Search Is Useful for a Travel Assistant

Vector Search could be useful if the Travel AI Assistant is expanded to include a knowledge base.

For example, the system could store:

Destination guides
Travel tips
Places of interest
Local culture information
Food guides
Historical information
Travel FAQs

These documents could be converted into embeddings.

A user could then ask:

"Where can I experience traditional culture in Jaipur?"

Instead of searching only for exact keywords, Vector Search could retrieve information that is semantically related to the question.

21. Embeddings

An embedding converts text into a numerical vector.

Conceptually:

"Best places to experience local culture"
                    ↓
             Embedding Model
                    ↓
        [0.12, -0.43, 0.81, ...]

The resulting vector can be stored in a database.

When a user asks a question, the question can also be converted into an embedding.

The system can then search for vectors that are most similar.

22. Semantic Search

Vector Search enables semantic search.

For example:

User query:
"Where can I see traditional architecture?"

A keyword search might look for:

traditional
architecture

A semantic search can identify documents that discuss:

historic buildings
heritage sites
old city areas
traditional structures

even when the exact words are different.

This is useful for AI applications because users do not always use the exact wording contained in the stored documents.

24. MongoDB Vector Search Index

MongoDB Vector Search requires an appropriate search index.

The index defines how vector data can be searched.

Conceptually:

MongoDB Collection
        ↓
Vector Field
        ↓
Vector Search Index
        ↓
Similarity Search

The index can also contain fields used for filtering.

For example, a travel knowledge collection could contain:

{
  "text": "Jaipur has several important heritage sites.",
  "destination": "Jaipur",
  "embedding": [0.12, 0.43, -0.21]
}

A vector index could then be created over the embedding field.

25. Automated Embeddings vs Bring Your Own Embeddings

MongoDB Atlas Vector Search can be used with different embedding approaches.

One approach is to use an integrated or automated embedding workflow where supported.

Another approach is:

Bring Your Own Embeddings

In this approach, the application generates embeddings using an embedding model and stores the resulting vectors in MongoDB.

For an AI application, the embedding model and vector dimensions must be compatible with the vector index configuration.

26. Current Vector Search Status

MongoDB Atlas is currently implemented in the Travel AI Assistant.

However, MongoDB Vector Search is not part of the current working MVP implementation.

The current database is primarily used to store generated travel itineraries.

Therefore, the current system does not yet perform:

Document Embeddings
        ↓
Vector Storage
        ↓
Vector Search
        ↓
Semantic Retrieval

Vector Search is documented as a future extension rather than being falsely represented as an implemented feature.

32. Conclusion

MongoDB Atlas is the persistent storage layer of the Travel AI Assistant.

The Node.js gateway connects to MongoDB Atlas and stores generated travel itineraries in the trips collection.

Each trip is associated with the authenticated Firebase user and contains the destination, trip details, interests, AI-generated itinerary, and creation timestamp.

MongoDB's document model is particularly suitable for the nested itinerary structure.

MongoDB Vector Search was also studied as a potential extension. It can support semantic search using embeddings and could eventually be used to build a Retrieval-Augmented Generation system for travel knowledge.

The current MVP intentionally keeps the architecture simpler:

Firebase
   ↓
Node.js
   ↓
FastAPI
   ↓
OpenAI
   ↓
MongoDB Atlas
